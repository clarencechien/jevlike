所見 01 · 答到哪裡

八個問題的狀態

v1 交接文件列了八個實驗要回答的問題。已答 是在合成資料上完整回答、與 GPU 無關的；上界 是延遲類，L4 的頻寬接近 GB10 但算力較弱，數字只能當保守上界；合成版 是門檻類，方法對了但數值要用真實資料重做。

Q1 · 上界

GB10 上的決策延遲 p50 / p95，比生成 JSON 快幾倍

L4 上單題 p50 206 ms、p95 225 ms（開 --swa-full 後 137 ms，decode 地板 26 ms）；同題生成 JSON 496 ms，typed 快 2.4–3.6 倍。

GB10 待補 · GB10 重跑 L1–L7，約 30 分鐘

Q2 · 已答

哪些 task 零樣本就夠、哪些要改題、哪些救不回

7 個 task test 準確率 ≥ 0.98；3 個（UPH 是否異常、SPC 動作、alarm 急迫度）0.82–0.93 但 top-2 / AUROC ≥ 0.99，是門檻與 criteria 問題；沒有救不回的。

GB10 待補 · 合成資料版；真實資料會低一些

Q3 · 已答

多題共用 state 的成本

預設下 10 題 = 7.1 倍，前綴 cache 完全沒命中；開 --swa-full 後 10 題 = 3.9 倍，第 2 題起每題 73 ms。

GB10 待補 · 倍數可信，絕對毫秒數以 GB10 為準

Q4 · 上界

生成負載對決策延遲的影響

背景持續生成 512 token 時決策 p50 206 → 285 ms（1.39 倍）；併發 4 / 8 client 的 p50 736 / 1437 ms，throughput 卡在 5.5 req/s，llama-server 在 L4 上沒把 prefill 批次化。

GB10 待補 · GB10 併發行為要重量，再決定要不要獨立 E4B

Q5 · 已答

中文 vs 英文 alarm

中文夾機台代碼普遍不輸英文；英文 alarm log 在 4 個 task 略差（急迫度 0.71 vs 中文 0.84），主因是英文樣本刻意寫得極簡。不需要先正規化中文。

GB10 待補 · —

Q6 · 合成版

每個 task 的信心門檻

raw 信心平均 0.99，無鑑別力：急迫度在 raw ≥ 0.9 的 coverage 0.97 但準確率只有 0.84。校準後 ≥ 0.9 才可用：SPC 動作 0.97 @ coverage 0.86，急迫度 1.00 @ 0.40。7 個強 task 用 raw ≥ 0.9 即可。

GB10 待補 · 用 200–500 筆真實 alarm／工單重做校準

Q7 · 已答

標註量：傳統 ML 與 typed decision 各要幾筆到 90%

TF-IDF + LR 在 100 筆內沒有一個 task 到 0.9（hard 子集 0.46–0.57）；typed decision 7 個 task 0 筆就 ≥ 0.98，弱的 3 個用 25 筆校準即可在 0.79–0.93 coverage 下達 0.95+。主管版「幾百筆」的說法成立，且多數 task 是 0 筆。

GB10 待補 · 資料集每 task 只有 200 筆，N > 100 量不到

Q8 · 已答

規則基線在哪些 task 夠用

沒有 task 的關鍵字規則 ≥ 0.95；最高是工單狀態 0.87（easy 0.96）。不建議任何 task 只用規則，規則可當 easy 案例的前置過濾。

GB10 待補 · —

Smoke 時就看到的現象在兩千筆上重現：模型幾乎永遠給 99% 的信心，對錯都一樣。alarm 急迫度的 raw ECE 是 0.178，temperature 要拉到 T ≈ 6 才校準得回來。所以 Jev 式「低信心就升級 LLM」的分流，在這個模型上只能用校準後的信心，raw 信心當門檻等於沒有門檻。

判定：不需要 fine-tune

三個弱 task 的 top-2 準確率與 AUROC 都 ≥ 0.99，排序能力沒問題。依 v1 的判讀順序，這是門檻與 criteria 的事：用 25–100 筆做 affine 校準，加上把「連續幾點、超限幾次、機台停多久」寫成可數的邊界，再看要不要動模型。

所見 03 · 延遲

單題兩百毫秒，但前綴 cache 預設是關不掉的壞

L4 上一題約 191 個 prompt token 的決策 p50 206 ms，同一題改讓模型生成 JSON 要 496 ms。這個倍數（2.4x）在 GB10 上大致會保留；絕對值會變。

Gemma 4 用 sliding-window attention，llama-server 預設的 SWA cache 只能整段命中、不能部分重用前綴——所以「多題共用 state」在預設下一毛錢都省不到。

另外兩個延遲所見：背景持續生成 512 token 時決策慢 1.39 倍；併發 1 / 4 / 8 個 client 的 p50 是 211 / 736 / 1437 ms，throughput 停在 5.5 req/s。llama-server 在 L4 上沒有把 prefill 批次化，併發只是排隊。這一項在 GB10 上要重量，才能決定要不要走路線 C（獨立一個 E4B 做高頻 gating）。

所見 04 · 標註量

「幾百筆」的說法成立，而且多數 task 是零筆

主管版報告承諾「標註需求從每題幾千筆降到幾百筆」。在三個 task 上從 calibration 集抽 N 筆、跑 3 個 seed，畫傳統 ML 和 typed decision 的學習曲線。下面是最弱的 SPC 動作；另外兩個 task 的 typed 零樣本本來就在 0.98 以上。

所見 06 · 沒答的

這一版說不了的三件事

延遲絕對值

全部是 L4 上界。GB10 用 bench/latency.py --only 重跑 L1–L7 約 30 分鐘，記得開 --swa-full。

真實資料的門檻

校準用的是合成資料，easy 例子是模板展開、規律性高。零樣本數字在真實 alarm 上會降，Q6 的門檻要用 200–500 筆真實資料重做。

併發與 aarch64

L4 上 llama-server 不因併發加速，GB10 要重量；模型檔若不是 UD-Q4_K_M，準確率也要在 GB10 重跑一次，同格式的 raw logprobs 可直接進 analyze.py。

還沒說到的

AI Studio 上的 Gemma 4 不開放 logprobs，31B dense 的對照因此沒做；env 裡的 Gemini key 這次只用來探測能力。實際費用 GPU 約 0.85 小時、約一美元，比交接文件估的 4–6 小時低很多，因為 A4B MoE 在 L4 上每題只要兩百毫秒。
