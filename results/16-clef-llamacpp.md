# 16 — Clef 走 llama-server、jevify 同底模對照、26B 換新版（v11，2026-10-03）

計劃與判定門檻：`docs/handoff-v11-clef-llamacpp.md`（跑前寫死）。完整表格：`results/16-clef-llamacpp-tables.md`（`bench/analyze_v11.py` 產生），數字：`results/v11.json`。
全部是合成資料。llama.cpp 釘 tag `b11371`（= commit `99b9548`，PR #29831 合併點），在 Modal 上從原始碼編；GGUF 與 jevify 都釘 revision。

## 一句話

**llama-server 的 Clef 跟 Cloudflare 原版等價，Q8／Q4 量化也可用，v10 卡住的「只能 transformers BF16」解開了。但速度沒有贏 26B，所以判斷層預設仍不換。
27B 改成可以用 Q8（29 GB）、llama-server 上 GB10，列為 SPC、重排序、同 state 多題的候選。jevify（同一顆 Gemma 26B 加英文通用 LoRA）在我們的題上比零訓練差，不採用；
要訓練就得用自己的產線資料。26B 換到 b11371 數字不漂，GB10 只需要一個 llama.cpp 版本。**（handoff 三句中選第二句，jevify 選第二句。）

## 0. 讀程式碼的發現（步驟 0，跑前）

- **溫度**：Clef GGUF 沒存溫度，server 套 1.0，機率可以直接跟 v10 比。
- **prompt**：`conversion/clef.py` 的 systemone 模板逐段照搬 `joint_schema_model.encode_record`，連 noul 的預設描述都一樣，而且逐段分開 tokenize。
- **choice 選項照 ID 排序**（`choice_sorted = true`），**題目保留請求順序**（`common_json` 保留插入順序），跟 Python 版一致。
- **機率沒有四捨五入**。
- **限制**：判斷層每次讀整個 batch，**多個 slot 不能一起算**，實際上一次一個請求（吞吐不隨併發增加，§4 有數字）；整個 prompt 要放得進一個 ubatch；跑 Clef 的 server 只提供 `/v1/systemone`；只支援文字。
- **release**：`b11371` 有 tag，但 release 壓縮檔還沒上傳；llama.cpp 本來就不出 Linux CUDA 預編檔，所以在 Modal 上編（image builder 太慢，改用 32 核 CPU function 編，binary 存 volume）。

## 1. 等價與量化

| arm | 對 v10 參考值最大機率差 | 答案一致 | 完整 D0（2,000 題）與 BF16 差 | 判定 |
|---|---|---|---|---|
| flash BF16 GGUF（L40S） | 0.008 | 50/50 | — | **等價** |
| 27B BF16 GGUF（H100） | 0.009 | 50/50 | — | **等價** |
| flash Q8_0 | 0.071 | 50/50 | −0.30 點（p = 0.11） | 可用 |
| flash Q4_K_M | 0.113 | 50/50 | −0.35 點（p = 0.25） | 可用 |
| 27B Q8_0 | 0.044 | 50/50 | ±0（p = 1.0） | 可用 |

- v10 在 transformers 裡量化（FP8 出 NaN、int8／NF4 機率偏 0.23–0.26）的問題不在 Clef 本身，而在量化方式。llama.cpp 的 GGUF 量化把 gated delta net 的 gate 處理好了，答案 50/50 一致。
- 最大機率差仍超過 0.01，所以算「可用」不算「等價」：答案和準確率不變，信心值會小幅移動。上線時門檻要用量化版自己的分數重新反推。

## 3. 速度（同一張 L40S、同一個 b11371 build、batch 1）

| | 單題 p50 | 同 state 三題 p50 | 吞吐（題/秒，併發 1／4／8） |
|---|---|---|---|
| 26B（我們，`--swa-full`） | 56 ms | ≈ 150 ms（1 題 87、5 題 212 ms 內插） | 17.7 / 18.7 / 18.1 |
| flash BF16 GGUF | 52 ms | 85 ms | 18.8 / 20.5 / 19.9 |
| flash Q8_0 | 48 ms | 84 ms | 21.0 / 22.1 / 22.1 |
| flash Q4_K_M | 45 ms | 80 ms | 22.1 / 23.1 / 23.0 |
| 27B Q8_0 | 142 ms | 256 ms | 6.9 / 6.9 / 6.9 |

- **flash 只快一點**：單題 0.85 倍，三題一起 0.56 倍，都沒到「0.5 倍」的門檻。v10 用 transformers 時 flash 61 ms、27B 87 ms（H100），llama-server 把 flash 拉到 48 ms，但 26B 在新 build 上本來就有 56 ms。
- **27B 是 26B 的 2.5 倍**（142 對 56 ms），超過 GB10 的 2 倍上限。dense 27B 每題計算量約 26B-A4B 的 9 倍，這在 L40S 上也看得到。
- **吞吐不隨併發增加**：Clef 每次讀整個 batch，一次只能算一個請求（§0）。26B 在 L40S 上也大致持平，所以這項兩邊打平。

## 4. jevify（同一顆 Gemma 4 26B-A4B，英文通用資料訓練的 LoRA；L4、llama-server b11118）

| | 26B（零訓練） | J1 jevify 原用法 | J2 jevify 權重＋我們的 prompt | J3 底模＋`--lora` |
|---|---|---|---|---|
| D0 平均 | **95.5%** | 92.5% | 93.6% | 92.7% |
| SPC／根因站別 | 86% / 98% | 78%（p=0.039）／ 90%（p=0.021） | 81% / 95% | 79% / 88%（p=0.013） |
| ECE（raw → 校準後） | 0.044 → 0.027 | 0.080 → 0.040 | 0.069 → 0.035 | 0.077 → 0.040 |
| 護欄外部題 | 74.5% | 89.1% | 87.3% | 90.9% |
| 工具守門 | 90.0% | 75.0% | 80.0% | 76.0% |
| JevBench 公開 231 | **88.7%** | 84.4% | 85.3% | 85.7% |
| 單題 p50（L4） | 206 ms（同 server 參數） | 248 ms | — | 259 ms |

- **J-a 訓練有價值：不成立**。D0 掉 2–3 點，SPC 與根因站別顯著變差；不擬溫度的 ECE（0.080）也沒比我們擬過溫度（0.027）好。只有護欄外部題變好（跟 Clef 一樣），工具守門變差。
  英文通用資料訓練的 LoRA 搬到中文產線題上沒有幫助；要訓練得用自己的資料。
- **J-b 混用**：生成 scale 0 跟不載 LoRA **逐字相同 50/50** ✓；J3 對 J1 單題延遲 1.04 倍 ✓；J1 與 J3 答案一致 **97.2%**，門檻 98% ✗（推測差在「LoRA 套在量化過的底模上」對「先合併再量化」，沒有另外驗證）。
- **混用的延遲代價**：判斷題與生成交錯時，不載 LoRA 判斷 p50 252 → 340 ms（1.35 倍，代價由生成吸收：13 tok/s）；載 LoRA（判斷 1、生成 0）252 → 1,110 ms（p95 2,796 ms），
  因為 scale 不同的請求不能同批算，判斷要排在生成後面。**判斷層要即時的話，不要跟生成共用一份帶 LoRA 的 server。**
- **J-c 速度**：jevify 單題比我們慢約 20%（248 對 206 ms），推測是 prompt 較長、要 top-20 logprob，沒有另外驗證。

## 5. 26B 換到 b11371（判定 D）

同一張 L4、同一組 server 參數重跑 D0：`bench/verify.py --check-lock` **0 項失敗**，2,000 題中 1,998 題答案相同，準確率 94.5% 對 94.5%。
→ GB10 上 26B 與 Clef 兩個 llama-server 可以用同一個 llama.cpp 版本（≥ b11371）。

## 6. 判定（對 handoff §5）

- **A 實作正確**：✓（兩個 BF16 GGUF 都等價）。
- **B 速度**：✗。flash 單題 0.85 倍、三題 0.56 倍（門檻 0.5）；27B 2.5 倍（門檻 2）。
- **C 準確率不掉**：✓（量化版與 BF16 差 ≤ 0.35 點，v10 過的格照樣過）。
- **D 26B 新版不漂**：✓。
- **jevify**：J-a ✗、J-b 兩過一差一點、J-c ✗。

## 7. 對上線的意思

1. **判斷層預設仍是 26B 讀字母**。flash 沒有快到值得換、準確率還略輸；27B 準但慢 2.5 倍。
2. **Clef 27B 的部署障礙解除了**：Q8_0（29 GB）跑 llama-server，GB10 放得下，跟 26B 用同一個 llama.cpp 版本。要不要接 SPC 與重排序，看 GB10 上的延遲：L40S 上 142 ms，GB10 算力更低，預期更慢。
3. **同 state 要問多題時**，Clef 三題一起不掉準確率，flash Q8 84 ms 對 26B 約 150 ms，是唯一接近門檻的速度優勢。
4. **jevify 不採用**；混用 LoRA 會讓判斷延遲被生成拖住，即時判斷不要這樣部署。
5. **自己訓練 LoRA** 仍是選項，但這一輪的證據是：通用資料不夠，要用產線資料，而且部署上要給判斷層獨立的 server。

## 8. 偏離計劃之處

- llama.cpp 改在 32 核 CPU function 編（image builder 太慢），binary 存 volume；libcuda 連到 toolkit 的 stub。
- J1 直接用 jevify 的 library（llamacpp 預設路徑），沒有自己重寫 prompt，也就沒做「jevify transformers 20 題參考」。
- jevify 的字母 ID 正反序 arm 有跑但不分析（jevify 依插入順序給字母，正反指派沒有意義）。
- 27B BF16 GGUF 只跑 smoke（H100），27B 的「可用」對照用 v10 transformers BF16（已證明與 BF16 GGUF 等價）。
- 26B 三題延遲沒有直接量 K=3，用 1 題與 5 題之間內插。
- 混用的對照組（不載 LoRA 的交錯）是跑完 J3 後追加的。
- 成本見 `results/cost.md`。
