# 17 — 輸入要怎麼準備：JSON 還是文字、要不要先算好、雜訊欄位（v12，2026-11-05）

計劃與判定門檻：`docs/handoff-v12-input-format.md`（跑前寫死）。完整表格：`results/17-input-format-tables.md`；錯誤樣本：`results/17-input-format-errors.md`（`bench/analyze_v12.py` 產生）；數字：`results/v12.json`。
資料：`data/v12/`（`gen_v12.py --seed 12`，六類 × 120 個事件 × 五種寫法，盲審兩輪見 `SPOTCHECK.md`）。全部是合成資料。
上線指南：**`docs/input-guide.md`**。

## 一句話

**格式（JSON 或文字）平均差不到 2 點，但單一類可差 5–13 點、方向不一；前處理很重要：要比數字的題，先算好 26B +8～+15 點（E4B +22、Clef +9），雜訊欄位 −3.6 點。
工具守門的「參數超規格」因此從 80% 到 100%，但「跨線範圍」先算好也還是 50%，要交給程式規則。**（handoff 三句中選第一句，附「格式不是完全不重要」的但書。）

## 1. 設計回顧

同一個事件寫成五種：T0 文字原始值、T1 文字＋衍生、J0 JSON 原始值、J1 JSON＋衍生、JN J0＋6–10 個無關欄位。gold 由事件與規則決定，五種寫法同 id，可逐題配對（McNemar exact）。
六類：急迫度、原因分類、派工、SPC、UPH、工具守門；每類 60 組 twin，其中 30–60 組只改一個數字讓答案換（numeric twin）。
三個模型都在 **L40S**、llama.cpp b11371、batch 1（`--workers 1`）：26B UD-Q4_K_M（主判）、E4B Q8_0、Clef 27B Q8_0（`/v1/systemone`）。

## 4. 錯在哪（`17-input-format-errors.md` 有每類 10 個 T1 對、J0 錯的樣本）

### 4.1 沒先算好時：模型看表面線索，不比數字，而且很有把握

26B 在 T1 對、J0 錯的有 96 個事件，模式一致：
- **回焊爐溫度低於上限仍判「停線」**（數字型 twin：J0 75%、T0 50%）：看到「溫度＋上限」就當成超限，機率 0.96–1.0。
- **原因分類的氣壓題**：廠務供氣 5.8 bar（下限 5）正常，仍判「環境」（J0／T0 都 50%＝兩個 twin 選同一個答案），先算好「廠務端低於下限：否」後 J1 100%、T1 90%。
- **派工的復歸次數**：本班 3 次、上限 5 次，仍判要派工（T0 57%、J0 70% → T1 83%、J1 93%）。
- **工具守門參數超規格**：temp_c 227 vs 230–250，J0 判「詢問」（80%）；先算好後 100%。
- 這 96 個錯誤裡 83 個（86%）選中答案的機率 ≥ 0.95，中位數 0.9997：**信心值抓不到「沒比數字」的錯**。先算好後 ECE 0.18–0.20 降到 0.10–0.12。

### 4.2 先算好只算一部分：會把模型推向被算的那一部分

- **工具守門的角色題**（操作員改規格內參數 → 拒絕；技術員 → 詢問）：T0 100%，T1 掉到 **54%**。
  T1 括號裡列了「寫入、可復原、影響線數 1、在負責線別內、參數在規格範圍內」，全部指向「詢問」，唯一決定答案的「呼叫者是操作員」沒有衍生欄位，模型就跟著括號走（11/12 錯成 B）。J1 沒有這個問題（95.8%）。
- 教訓：衍生欄位要覆蓋判斷標準的**每一個**面向（角色權限也要查表寫出來），或者乾脆不給。

### 4.3 衍生欄位名字不清楚：模型會誤讀

- **SPC「恰好一點接近界限」（gold 持續監控）**：J0 90.6%、T1 100%，但 J1 只有 **56.2%**，14/16 錯成「抽檢」。
  J1 帶了 `"max_beyond_2sigma_in_3":1`（三點內超過 2σ 的最多點數 = 1，規則門檻是 2），模型把「有值」讀成「觸發」。T1 同一個資訊寫成「任 3 點中超過 2σ 最多 1 點」就全對。
- 教訓：給規則**結果**（`"rule_2of3_beyond_2sigma": false`）或白話句子，不要給要再跟門檻比一次的中間計數。

### 4.4 有些規則先算好也不套：交給程式

- **跨線暫停（工具守門 multi_line_scope）**：三個模型五種寫法幾乎都是 50%——跨 2–4 條線的暫停也判「詢問」。J1 明寫 `"lines_affected":2` 仍然一樣。v9 的結論（範圍交給規則）不變。
- **急迫度「超限＋爐內有板（停線）」對「超限＋已自動停止進板（盡快）」**：五種寫法 50–60%，跟格式與數字無關，是標準本身模型不套。要改判斷標準或用規則。

### 4.5 雜訊欄位

JN（加 event_id、uuid、ts、韌體版本、PLC 位址…）對 J0：26B −3.6 點、E4B −3.5、Clef −1.7；token 多 39%，延遲多 15%。
傷害集中在「要比對兩個欄位」的題：工具守門「讀別條線」26B 96 → 65%、「參數超規格」80 → 68%、SPC 連 7 點 60 → 45%。

### 4.6 JSON 對文字

六類平均差在 2 點內，但類別之間方向相反：
- JSON 較好：UPH（+7.5，T0→J0）、急迫度原始值（+8.3）、SPC 原始值（+10.8）、工具守門先算好（+8.3）。
- 文字較好：原因分類（−7.5／−7.5）、派工先算好（−5.8）、SPC 先算好（−12.5，即 §4.3 的欄位名問題）、電壓題（T1 100% 對 J1 50%）、單站停機題（T 100% 對 J 56–69%）。
- 三個模型裡，最好的寫法都是 **T1**（26B 89.2、E4B 82.2、Clef 90.7）；Clef 的 T1→J1 −3.2 顯著（p = 0.001）。

## 5. 對上線的意思

1. **前處理是主要的槓桿**：數字比較、代碼查表、SPC 規則統計一律程式先算，寫成「結論＋數字」（「超出上限：是（+14°C）」），保留原始值。
2. **衍生要完整或不給**：只算一部分會偏向被算的面向（§4.2）。
3. **給結果不給中間計數**，名字用白話（§4.3）。
4. **送進模型前拿掉 ID、時間戳、韌體版本等欄位**（§4.5）。
5. **格式預設用中文句子模板（T1 型）**：三個模型都最好；手上是 JSON log 就用程式轉成句子，不要直接丟 JSON。要用 JSON 也行，但每類在 GB10 上用真實資料驗過再上。
6. **模型不套的規則（跨線範圍、爐內有板）用程式規則先擋**，不要指望寫法能救。
7. 先算好也讓信心值比較可信（ECE 降一半），但門檻仍要用真實資料重新反推。

可照做的版本：`docs/input-guide.md`。

## 6. 偏離計劃之處

- **硬體**：handoff 寫 L4，Modal 當時 L4 排不到（等 15 分鐘未排程），26B 與 E4B 改在 L40S 跑。準確率不受影響（同一個 build、同一組 server 參數）；延遲是 L40S 數字，只拿來比 JN／J0 比例。
- **T1 保留原始值**：handoff 範例的 T1 只寫「超上限 9°C」，這裡寫成「254°C，上限 245°C（與上限差 +9°C，超出上限：是）」，讓 T1 與 J1 資訊對等（MANIFEST 有註）。
- **token 數**用 llama-server 回傳的 `prompt_tokens`（整個 prompt，含題目與選項），不是另外呼叫 `/tokenize` 只算 state；三種寫法題目相同，差值就是 state 的差。
- **Clef 沒有記錄延遲**（rows suite 不量）；Clef 的速度見 v11。
- **抽查兩輪**：第一輪 10/72 事實不一致（14%，急迫度的「持續中／運轉中」只在文字版），改產生器重生；第二輪 3/72（4.2%）仍補完才開跑。兩輪審查者的答案與 gold 144/144 一致。
- 跑前做了一次 26B 小量 smoke（每類 5 題 × T0／J0，舊版資料），不計入結果。
- 成本見 `results/cost.md`（L40S 約 0.5 小時、約 $1）。
