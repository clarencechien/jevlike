# 15 — Cloudflare Clef / Clef-flash 同尺對照（v10，2026-10-02）

計劃與判定門檻：`docs/handoff-v10-clef.md`（跑前寫死）。完整表格：`results/15-clef-tables.md`（`bench/analyze_v10.py` 產生），數字：`results/v10.json`。
全部是合成資料；權重 Apache 2.0，從 HF 釘版下載到 Modal volume，不進 repo（Clef `2f3de3dd…`、Clef-flash `17f0b0ad…`）。

## 一句話

**Clef 27B 在我們的中文產線題上比 26B 準（D0 96.6% 對 95.5%，SPC +11 點、重排序 nDCG@5 0.879 過門檻），Clef-flash 略輸（93.0%）；但兩者在本機都沒有速度優勢，
而且只能用 transformers BF16 跑：判斷層讀的是每個位置的 hidden state，推論引擎接不上，量化版全部沒過等價檢查。所以判斷層先不換，27B 留作「弱題與重排序」的候選，
到 GB10 上量真實延遲再決定。**（handoff 三句結論中選第二句，並補上 27B 的準確率優勢。）

> **v11 更新（2026-10-03）**：llama.cpp `b11371`（PR #29831）原生支援 Clef，下面 §0「判斷頭接不上推論引擎」與 §1「量化版全部不等價」已不成立：
> llama-server 的 BF16 GGUF 與本頁的 transformers 版等價，Q8／Q4 可用；但速度仍沒贏 26B，結論「預設不換」不變。見 `16-clef-llamacpp.md`。

## 0. 讀卡發現（跑前不知道的事）

- **判斷層接不上推論引擎**：joint schema head 讀 backbone **每個位置**的最後一層 hidden state（state、問題、每個選項的 span 平均，再做 cross-attention），
  加上 lm_head 權重當詞彙錨點。vLLM、SGLang、llama.cpp 都只吐 logits 或最後位置，沒有辦法跑這個頭。模型卡本身沒寫支援這些引擎；HF 頁面上依架構自動列出的 vLLM／llama.cpp 入口與任何 GGUF 轉檔，跑起來只有 backbone，是一般生成模型，**不是 Clef**。
  所以計劃 §3 的「最佳化 runtime 等價檢查」不成立，唯一 runtime 是 transformers；量化只能在 transformers 裡做（FP8、int8、NF4）。
- **choice 選項會先照 ID 排序**：`question_options()` 對 choice 做 `sorted()`，所以「把選項反過來送」對 Clef 是同一個輸入。順序測試改成把 ID 換成字母、正向／反向指派（§2）。
- **預設 `max_length` 16,384**，不是新聞寫的 64K（backbone 的 position 上限是 262K，16K 是這份程式碼的預設截斷）。
- **新聞的 CLINC150 97.4 是 27B 的分數**；模型卡上 flash 是 66.8。官方 Decision Index 41 項裡，Jev 在 GPQA、MMLU-Pro、BBH 這類推理題明顯贏 Clef。
- 架構：Qwen3.5 混合注意力（每 4 層 3 層 gated delta rule linear attention、1 層 full attention），flash 32 層、27B 64 層，都是 **dense**。

## 1. 等價檢查（D0 抽 50 題，對 BF16 參考值）

| arm | 最大機率差 | 答案一致 | acc | 等價（≤ 0.01 且 ≥ 49/50）？ |
|---|---|---|---|---|
| flash FP8（block 128） | **NaN** | — | 36%（全 NaN，argmax 落在第一個選項） | ✗ |
| flash FP8，linear attention 留 BF16 | 0.096 | 49/50 | 92% | ✗ |
| flash int8（bitsandbytes） | 0.232 | 49/50 | 96% | ✗ |
| flash NF4 | 0.257 | 49/50 | 92% | ✗ |
| 27B FP8（L40S） | **NaN** | — | 36% | ✗ |

- FP8 的 NaN 來自 **linear attention 投影層**量化後溢位；那幾層留 BF16 就沒有 NaN，但機率仍偏 0.1。
- 依計劃：沒有量化版過 → 27B 主跑改回 **H100 BF16**，flash 只用 BF16。之後 `clef_run.py` 加了 NaN 防護，不會再把 NaN 算成答案。
- GB10 不受影響：BF16 的 27B 55 GB、flash 19 GB，128 GB 都放得下，**本來就不需要量化，也不應該用**。

## 2. 主結果（D0 test 半，每類 100 題，與 26B 同一個 test 半）

| | 26B（我們） | E4B | Clef-flash | Clef 27B |
|---|---|---|---|---|
| D0 平均 | 95.5% | 88.5% | 93.0% | **96.6%** |
| 弱題三類（急迫度、SPC、UPH） | 87.0% | 76.0% | 84.0% | **91.3%** |
| 中文（1,596 題，全部） | 95.2% | 89.5% | 94.1% | **97.1%** |
| 英文／中英夾雜（404 題） | 91.8% | 84.7% | 89.9% | **92.8%** |
| 手寫難例（600 題） | 91.2% | 83.3% | 88.7% | **93.3%** |
| D2 Gemini 盲寫（584 題） | 95.9% | 93.5% | 96.6% | 96.7% |
| ECE 校準後 | 0.027 | 0.059 | 0.037 | **0.025** |
| ε=5% 守住的類／平均自動處理 | 10/10、84.8% | 8/10、74.9% | 10/10、81.4% | 9/10、**94.5%** |
| JevBench 公開 231（self-run） | **88.7%**（hard 77.5%） | 78.8% | 81.8%（hard 64.0%） | 87.4%（hard 74.8%） |

逐類顯著差異（McNemar p < 0.05）只有兩個：
- **Clef 27B 的 SPC 判讀 97% 對 26B 86%（p = 0.007）**：這是我們九輪以來最難拉高的一類（v5 的 prompt 招數都沒用）。
- **Clef-flash 的根因站別 86% 對 98%（p = 0.004）**：flash 唯一明顯輸的一類。

**中文沒有掉**：英文意圖分類的成績在中文產線題上大致成立。27B 中文 +1.9 點，flash −1.1 點，都在判定 B 的 −2 點容忍內。

ε=5% 的錯誤預算：Clef 27B 是第一個能讓**急迫度**進自動段的模型（26B、flash 都是 0%）。但它在 test 上的實際錯誤率是 8.7%，超過 5%，就是 9/10 裡沒守住的那一類。
其餘 9 類自動處理 92–100%，比 26B 高（SPC 92% 對 69%）。

## 3. 順序敏感度

| | 翻面率（字母 ID 正向 vs 反向，D0 choice 1,200 題） | SPC | JevBench choice 反序 |
|---|---|---|---|
| Clef-flash | 1.8% | 8.0% | 5.8% |
| Clef 27B | 1.2% | 2.0% | 5.0% |
| 26B | — | 19%（v5，6–8 種字母輪換，量法較嚴） | 7.2% |

- 用標籤當 ID 時，Clef 的選項順序**由排序決定**，使用者怎麼排都一樣。這是設計上就消掉了順序問題，不是量出來的穩定。
- 換成字母 ID、真的反轉順序，翻面率也只有 1–2%。SPC 這一類 26B 是 19%（量法不同，不能直接相減，但差距大到方向不會錯）。
- 意外發現：字母 ID 比標籤 ID 準（27B 98.4% 對 97.1%、flash 95.2% 對 94.0%）。選項的中文標籤進了 lexical anchor，反而帶偏。上線時 ID 怎麼取要當成一個參數量。

## 4. v9 四格

| 格（門檻） | 26B | Clef-flash | Clef 27B |
|---|---|---|---|
| G 護欄：定誤擋 5% 攻擊 recall／誤擋 | 96.4%／4.5% ✓ | 96.4%／2.3% ✓ | 96.4%／2.3% ✓ |
| G 盲寫外部題 | 74.5% | 92.7% | **98.2%** |
| T 工具守門 acc（≥ 95%）／危險放行 C→A（≤ 1%） | 90.0%／0% ✗ | 85.0%／**2.7%** ✗ | 85.0%／**2.7%** ✗ |
| E 評分 Spearman／完全對 | 0.98／99.7% ✓ | 0.98／93.7% ✓ | 0.98／99.0% ✓ |
| R 重排序 nDCG@5（≥ 0.85） | 0.840 ✗ | 0.836 ✗ | **0.879 ✓** |

- **護欄的外部題是 Clef 最大的優勢**：26B 在 Gemini 盲寫的攻擊題只有 74.5%（v9 的限制），Clef 27B 98.2%。訓練判斷頭在「沒看過的寫法」上泛化比較好。
- **工具守門更差，而且出現危險放行**（真答案「拒絕」判成「允許」2.7%，26B 是 0）。v9 的結論不變：權限表寫成規則，模型不做這一格。
- **重排序 27B 過門檻**（0.879，比 BM25 高 0.225），是九格裡唯一被 Clef 翻成「過」的。

## 5. 三題一起判（Clef 原生的 joint schema，對照 v7 P1 packed readout）

| task | Clef-flash 單題 → 三題一起 | Clef 27B 單題 → 三題一起 | 26B packed readout（v7） |
|---|---|---|---|
| 急迫度 | 80.0% → 75.5%（p = 0.022），翻 7% | 83.0% → 83.5%，翻 9% | −14 點（p = 0.004），翻 18% |
| 原因分類 | 96.0% → 95.5% | 95.5% → 96.0% | ±0 |
| 派工 | 96.5% → 99.5%（p = 0.031） | 100% → 100% | −6 點 |

（Clef 是 alarm 三類全部 600 列；26B 是 v7 的 test 100 題。）
**27B 一次判三題不掉準確率**，這是我們自己做不到的（v7 P1 不採用）。flash 在急迫度上仍會互相帶偏。

## 6. 延遲（batch 1，第二輪計時；表頭一律「非 GB10」）

| | GPU | 單題 p50 | 三題一起 p50 | 首次遇到新長度 | 每題計算量 | 峰值顯存 |
|---|---|---|---|---|---|---|
| 26B-A4B（SGLang FP8，v6） | L40S | 63 ms | 3 題分開送 359–400 ms | — | 1.8 TFLOP | — |
| Clef-flash（transformers BF16） | L40S | 61 ms（另一次 run 46 ms） | 76 ms | ≈ 同 | 5.5 TFLOP（3.1×） | 19.4 GB |
| Clef 27B（transformers BF16） | H100 | 87 ms | 88 ms | **≈ 1,020 ms** | 16.5 TFLOP（9.3×） | 55.3 GB |

- **單題沒有比我們快**：flash 61 ms 對 26B 63 ms，判定 B 要求 ≤ 0.5×，沒過。Cloudflare 的 38.8 ms 是他們自己的 serving，transformers 做不到。
- **時間花在 Python，不在 GPU**：profiler 顯示每次呼叫的 GPU 時間只有 35 ms（flash）／40 ms（27B），其餘是 transformers 的 kernel launch 與 linear attention 的 Python 包裝。
  所以這些延遲是框架上限，不是模型上限。寫成 CUDA graph 或專用 serving 可能快一倍，但那是工程，不是這輪的事。
- **三題一起幾乎不加時間**：flash 61 → 76 ms、27B 87 → 88 ms。同一 state 問多題時，這是相對 26B（分開送 359–400 ms）真正的速度優勢。
- **H100 上每遇到一個新長度，第一次要 ≈ 1 秒**（fla 的 Triton kernel 依長度 autotune）；L40S 上沒有這個現象。上線要在啟動時把常見長度暖過一輪。
- **計算量**：26B-A4B 是 MoE，每 token 只啟用約 3.8B；Clef 是 dense。到 GB10 這種算力較低、Python 開銷差不多的機器上，flash 大概仍受框架開銷限制，27B 則可能變成受算力限制。**GB10 實測才算數**。

## 7. 判定（對 handoff §5）

- **A runtime**：✗。沒有推論引擎能跑判斷層，量化版全部不等價 → 「transformers BF16 可用、速度未最佳化」。
- **B Clef-flash 取代 26B**：**0/10 類**。準確率 9/10 類過（根因站別沒過），中文切片過，但速度 10/10 類沒過（61 對 63 ms，計算量 3.1×）。
- **C 訓練判斷頭有價值**：**成立（4 條中 2 條）**。弱題三類 +4.3 點 ✓（SPC +11）；重排序 0.879 ✓；工具守門 85% ✗；JevBench hard 74.8% ✗。
- **D 順序敏感度**：✓（SPC 2% 對 19%，量法不同，見 §3），加分項。
- **E 不換的條件**：沒有觸發（flash 中文 −1.1 點，ε=5% 守住 10/10）。

## 8. 對上線選型的意思

1. **判斷層預設不換**。26B 讀字母在速度上已經跟 Clef 一樣，D0 只差 1.1 點，而且有推論引擎（llama-server／SGLang）、prefix cache、量化版可用。
2. **Clef 27B 列為兩格的候選**：SPC 判讀（+11 點）與重排序（唯一過門檻）。前提是 GB10 上 BF16 27B（55 GB）和生成模型同時常駐的記憶體與延遲可以接受。
3. **同一 state 要問多題的場景**（alarm 一則問急迫度、分類、派工），Clef 27B 一次判完不掉準確率，是我們做不到的。
4. **護欄的外部題泛化**是 26B 的已知弱點（74.5%），Clef 27B 98.2%。若護欄要上線，這是換的理由。
5. **工具守門照舊用規則**；Clef 在這格更差，還出現危險放行。

## 9. 偏離計劃之處

- 計劃 §3 的「vLLM／SGLang 等價檢查」不可行（判斷層接不上），改成「transformers 內的量化版等價檢查」，多測了 FP8 去 linear attention 與 int8 兩個診斷。
- 順序測試改用字母 ID 正反指派（Clef 會排序選項）。
- 26B 的延遲沿用 v6 的 L40S 數字（同卡型、同設定），沒有重量。27B 的延遲是 H100（BF16 放不進 L40S），跟 26B 不同卡。
- 計劃的 K=7 延遲沒做（只有 K=3）。Workers AI arm 沒做（沒有提供 token）。
- 三題一起判的準確率用 alarm 三類全部 600 列（不是 test 半）。
- 成本見 `results/cost.md`（≈ $4.5，上限 $8 內）。
