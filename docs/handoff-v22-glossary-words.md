# Handoff v22 — 給它詞表、把英文字列成選項：讀字母抓 ASR 錯的第二次（2026-10-15，跑前寫死）

v21 的結論：讀辨識稿判「這段有沒有錯」，E4B 0.713、26B 0.777，輸給或只略勝 Breeze 自己的 logprob 0.726；
補算發現 logprob 與 26B **互補**（排名平均 0.802）。v21 給模型的題型是「在整段裡找」，而讀字母的本行是「在擺出來的選項裡挑」，
而且這一輪故意沒給領域詞表。v22 補這兩件，只在**英文錯**（標籤乾淨，雜訊地板 5%）上判；中文錯字照 v21 的代理正解只報不判。
不用人工校對、不碰音訊、不訓練。

## 0. 規則

- 語料、視窗、標籤、Breeze 輸出全部沿用 v21 的凍結檔（`data/v21/windows.jsonl` sha256 `224fe9e9…`、`results/modal/v21/breeze`）。不重切、不重標。
- E4B Q8_0、26B UD-Q4_K_M、llama.cpp b11371、純文字 `/completion` 讀字母（v21 的 `bench/v21_judge.py` 路徑），`--reasoning-budget 0`、不開 MTP。
- 詞表來源 = kikemu `terms.json`（每段的英文術語與變體，83 型）。**這是從正解抽的，含 Breeze 認錯的那些詞，所以「精確詞表」是上限，不是產線會有的條件**；產線條件用「混合詞表」近似（三段的詞表合併，三分之二是干擾詞）。
- 評分主指標：E 的 AUROC（視窗層）；per-word 臂另報「哪個詞錯」的詞層準確率。C 只報代理正解的 AUROC。
- 排名平均（rank average）是 v21 補算的做法，直接沿用：各訊號在 544 個視窗上的排名取平均。不擬參數，所以不需要折。

## 1. 臂（每臂 E4B 與 26B 各跑一次，544 視窗）

| 臂 | 題 | 選項 | 讀什麼 |
|---|---|---|---|
| **B 詞表** | state 前面加「這集的術語表：{該段的 term 與 variants}」；Q：「這一段有沒有術語表裡的詞被聽成別的字（例如 Bing 聽成 bin）？」 | A 沒有／B 有 | P(B) |
| **B′ 混合詞表** | 同 B，但詞表是三段合併（含干擾詞） | 同上 | P(B) |
| **C 列字** | 把這一段出現的英文字（去重、依出現順序，最多 9 個）列成選項，最後一項「都對」；Q：「哪一個英文字是聽錯的？」 | A…；最後字母 = 都對 | 視窗分數 = 1 − P(都對)；詞層 = argmax 是否命中對齊標出的錯字 |
| **D 列字 + 詞表** | C 的題，state 前面加 B 的詞表 | 同 C | 同 C |
| **（對照）A 原題** | v21 的 Q1，不重跑 | | v21 的 P(B) |

沒有英文字的視窗（544 − 267 = 277 個）C／D 臂不問，視窗分數記 0（它們不可能有 F2 認錯字，但可能有 F4 漏掉；報 coverage）。
詞層標籤：v21 對齊 detail 裡 kind F2 的 hyp 端英文字；一個視窗多個錯字時命中任一即算對。

## 2. 組合（純計算，不加呼叫）

- 每臂與 Breeze logprob（`d1_mean`）排名平均。
- 級聯：只在 logprob 最低的 40% 視窗問，其餘視窗分數沿用 logprob 排名；報 AUROC 與呼叫次數省多少。

## 3. 預測（寫死）

- E4B：B 0.80、B′ 0.77、C 0.76（詞層 0.55）、D 0.82；26B：B 0.86、B′ 0.84、C 0.80（詞層 0.65）、D 0.87。
- 排名平均加 logprob：E4B 最佳臂 0.84、26B 最佳臂 0.87。級聯只問 40% 時掉 ≤ 0.02。
- C（代理正解）：各臂 0.60–0.68，不變。
- 混合詞表比精確詞表掉 0.02–0.04。
- 選項數隨英文字數變（2 到 10），字母先驗照 v19 接近均勻，不做旋轉；但 C 臂「都對」固定在最後一個字母，報它的 P 分佈當位置檢查。

## 5. 階段

1. `bench/v22_judge.py`：在 v21_judge 的骨架上加 `--arm glossary|glossary_mixed|words|words_glossary`（state、題、選項）；詞表由 `data/v21/kikemu/terms.json` 產生；英文字從視窗 text 用 v21 的 tokenizer 抽。
2. `modal_v22.py`：同 modal_v21 的 judge 容器，四臂 × 兩引擎，八個容器並行，每個約 3 分鐘；smoke 先跑 10 個視窗看 option mass ≥ 0.9 與「都對」的位置。
3. `bench/analyze_v22.py`：臂 × 引擎 AUROC（E、代理 C）、詞層準確率、排名平均、級聯、門檻表 → `results/26-glossary-words.md`、`results/v22.json`。
4. 報告、README 一列、REPORT §3q、cost、番外篇 HTML 的「還能試」表補結果。

費用預估：Modal L4 約 0.6 h，≈ $0.5。

### 三件跑了才知道的事

1. **題型比詞表重要。** 把英文字列成選項問「哪一個聽錯」，E4B 從 0.713 升到 0.767、詞層 top-1 0.754；26B 詞層 0.899。同一個模型、同一段文字，差別只在「找」變成「挑」。這是讀字母的本行，v21 問錯了形狀。
2. **詞表對小模型有害、對大模型小補。** E4B 看到 499 個字的術語表之後反而更不會判（0.638）；26B 多 4 點。混合詞表（三分之二是干擾詞）沒有比精確詞表差，反而略高——模型不是在查表，是被「這集有這些詞」的語境提醒。
3. **「都對」這個選項的機率隨選項數掉。** 2–3 個英文字時「都對」平均 0.6–0.8，9 個時 0.04。選項一多模型幾乎一定標一個出來。視窗層的分數因此偏向英文字多的視窗；詞層準確率不受影響。要上線得按選項數校準「都對」的門檻，或限制每題 ≤ 4 個字。

### 預測對答案（15 條對 5 條）

對：E4B 列字 0.76（0.767）、26B 列字 0.80（0.799）、代理 C 不變、E4B 詞層 ≥ 0.55（0.754，高很多）、26B 詞層 ≥ 0.65（0.899，高很多）。
錯：E4B 詞表 0.80（0.638）、E4B 混合 0.77（0.676）、E4B 列字 + 詞表 0.82（0.745）、26B 詞表 0.86（0.814）、26B 混合 0.84（0.820）、26B 列字 + 詞表 0.87（0.801）、加 logprob E4B 0.84（0.804）、26B 0.87（0.830）、級聯掉 ≤ 0.02（掉 0.04–0.07）、混合比精確掉 0.02–0.04（反而升）。

### 決定

- **閘門第二道若要加模型，用列字題型，不用「這段有沒有錯」。** E4B 列字 + logprob 0.804，跟 v21 的 26B 原題 + logprob 持平，所以 E4B 在這個位置可以取代 26B。
- **26B 列字可以直接把「哪個詞錯」回給人**（詞層 0.90）。這是複核介面要的東西：不是「這段可疑」，是「bin 這個字可疑」。
- 詞表不給 E4B；給 26B 可以，不必精確。
- 不級聯，全問：每視窗一題 250 ms（E4B）或 410 ms（26B），544 視窗 2–4 分鐘。
- 仍沒有臂到 0.85，不是產線級閘門；要再往上得先按選項數校準「都對」，然後才是真實錄音。

費用：Modal L4 八個容器各 1–2 分鐘加 smoke，第一次啟動因檔案變動失敗重跑一次，約 0.4 h、≈ $0.35。

## 7. 限制（跑前就知道的）

- 精確詞表來自正解，是上限；混合詞表是產線條件的近似，不是真的產線詞表。
- 語料仍只有 3 段講者；E 只有 117 個正例，AUROC 的 CI 約 ±0.05。
- 只做英文錯；中文錯字的題型（列字）做不了，因為中文沒有「字的邊界」可以列。
